Chapter 01

Why I Built This

Inspecting hydroponic leafy green tiers and ambient monitoring points in a vertical farm.

I spent time around a real vertical farming environment and saw firsthand how many physical variables shift throughout the day: greenhouse microclimates, irrigation line pressure, dosing pumps, lighting photoperiods, and biological crop conditions.

Being around that physical operation created the initial engineering question: what does an end-to-end data platform behind modern CEA look like—from high-frequency sensor streams to historical dimensional modeling?

Because the local agricultural company's identity, operational telemetry, and internal architecture are strictly protected by a Non-Disclosure Agreement (NDA), I cannot publicly publish proprietary datasets or internal systems.

Instead of abandoning the engineering problem, I chose to recreate it publicly. I built a standalone multi-threaded Python telemetry generator and engineered a full-lifecycle Microsoft Fabric platform around it.

Why I built the public platform: I did not build this to collect another technology badge or claim years of enterprise senior expertise. I built the public version to understand whether I could take an engineering problem from data generation through streaming ingestion, medallion curation, dimensional modeling, analytics, monitoring, and operational alerting—and critically evaluate its tradeoffs.

Public Recreation Under NDA

HydroGrow Solutions is a fictionalized case-study identity created specifically for this public demonstration. The public repository contains 100% synthetic telemetry generated by Python, ensuring complete transparency and interview defensibility while preserving confidentiality.

class EnvironmentalTelemetryGenerator(BaseTelemetryGenerator):
    """Generates continuous microclimate readings for vertical growing zones."""

    def generate_event(self) -> EnvironmentalTelemetryEvent:
        facility = self.random_manager.choice(self.settings.facilities)
        zone = self.random_manager.choice(facility.zones)
        
        # Calculate diurnal solar cycle & HVAC thermal response
        ambient_temp = self.environment_manager.get_zone_temperature(facility.id, zone.id)
        relative_humidity = self.environment_manager.get_zone_humidity(facility.id, zone.id)
        co2_ppm = self.environment_manager.get_zone_co2(facility.id, zone.id)
        
        # Intentional anomaly injection for testing Fabric Activator alerts
        if self.settings.enable_ingestion_anomalies and self.random_manager.random() < 0.02:
            ambient_temp += self.random_manager.uniform(8.5, 14.0)  # Thermal runaway spike

        return EnvironmentalTelemetryEvent(
            event_type=EVENT_TYPE_ENVIRONMENTAL,
            facility_id=facility.id,
            zone_id=zone.id,
            sensor_type="ambient_temperature",
            sensor_value=round(ambient_temp, 2),
            unit="celsius",
            sensor_status=SENSOR_STATUS_HEALTHY if ambient_temp < 32.0 else SENSOR_STATUS_WARNING,
            is_daytime=self.environment_manager.is_daytime(),
        )

Layer 01 — Streaming & Operational Path

Real-Time Ingestion & Eventhouse KQL Database

Events from the Python simulator are received by Microsoft Fabric Eventstream via a dedicated Custom App endpoint. The stream partitions and routes events to 9 specific targets. Real-time telemetry is ingested directly into SmartFarmingKQLDB inside an Eventhouse, where continuous update policies and materialized views pre-aggregate microclimate metrics.

Layer 02 — Historical Analytics Path

OneLake Medallion Architecture (Bronze ➔ Silver ➔ Gold)

Historical telemetry is curated within SmartFarming_Lakehouse using Microsoft Fabric custom schemas. Data quality progressively increases as records move from raw append files to cleansed tables and finally into a production Kimball Star Schema.

Layer 03 — Data Warehousing

Kimball Dimensional Model (6 Dimensions, 8 Fact Tables)

Rather than building isolated KPI aggregates, the Gold layer models the farming domain into conformed dimensions (facilities, zones, crops, equipment, technicians, dates) and granular business facts (environmental daily, equipment telemetry, crop yield, maintenance SLA, and dead-letter governance).

Conformed Dimensions

8 fact tables covering operations, biological yield, SLA, and governance
Storage Optimization
Z-Order clustering on (facility_id, timestamp) for partition pruning
Layer 04 — Business Intelligence

Power BI Direct Lake Semantic Modeling

The enterprise semantic model (defined in TMDL format) connects directly to Gold OneLake Delta Parquet files using Direct Lake mode. This queries cold storage data directly with in-memory performance, completely bypassing scheduled import refreshes and dataset size limits.

Layer 05 — Incident Response & DataOps

Real-Time Alerting (Fabric Activator) & 5-Worker DLQ Remediation

Fabric Activator (Reflex) monitors live streaming events and triggers automated actions for operational farm anomalies (pH drift, thermal spikes) and DataOps engineering issues (ingestion latency, DLQ spikes). Corrupted payloads are quarantined into a dedicated Dead-Letter table and remediated via an automated 5-worker notebook process.

Layer 06 — Security & Governance

Regional Row-Level Security (RLS) & Dynamic Data Masking (DDM)

Security is enforced at the warehouse engine level using an inline table-valued predicate function (fn_SecurityPredicate_FacilityRegion) and Security Policies, ensuring regional facility operators can only view data from their assigned geographic jurisdiction. Sensitive operator contact info is dynamically masked using SQL DDM.

Chapter 07

Engineering Decisions & Defensibility

Detailed technical rationale behind architectural choices, interview-defensible tradeoffs, honest platform boundaries, and production deployment contrasts.

Why Eventhouse and KQL for the real-time path instead of relational SQL?

The Architectural Driver: In continuous IoT environments (8 facilities, 80 zones emitting multi-stream sensor events), relational database engines encounter severe transaction log contention and lock escalations during high-frequency micro-batch appends.

Why KQL/Eventhouse was Chosen: KQL (Kusto Query Language) is built on an append-only, distributed column-store architecture with automatic indexing on all columns. Eventhouse supports native continuous update policies, time-window bucket aggregations (bin()), and in-memory NVMe hot caching (7 days). This allows sub-second analytical queries across millions of raw telemetry rows without degrading streaming write throughput.

Engineering Tradeoff: Eventhouse does not support cross-table relational transactional integrity (ACID multi-statement transactions) or row-level mutations (UPDATE/DELETE). It is purely an append-and-aggregate engine, which is why historical dimensional transformations are routed separately to Delta Lakehouse.

Why build a Kimball Star Schema in Gold rather than querying raw Silver tables?

The Architectural Driver: Exposing normalized or semi-cleansed Silver Delta tables directly to business analysts forces complex multi-table joins, exposes technical identifiers, and duplicates business logic across separate Power BI reports.

Why Kimball Star Schema was Chosen: The Gold layer is organized into 6 conformed dimensions (facilities, zones, crops, equipment, technicians, dates) and 8 business fact tables. This provides a single, reusable source of truth for all downstream reporting. Conformed dimensions allow drill-across capabilities between operational telemetry facts (environmental, equipment runtime) and biological harvest yields.

Engineering Tradeoff: Maintaining dimensional tables requires surrogate key lookups and orchestration pipelines during batch sync. However, it drastically simplifies Power BI DAX calculations, eliminates circular join paths, and structures Delta Parquet files for maximum VertiPaq column compression.

Why Medallion Architecture (Bronze ➔ Silver ➔ Gold)?

The Architectural Driver: A data platform must separate raw data fidelity from analytical curation so that upstream ingestion errors never corrupt analytical reporting and historical raw data can always be reprocessed.

How it Works in this Platform:

  • Bronze: Immutable raw landing via Zero-Copy Fabric shortcuts. Retains raw JSON schema for auditability.
  • Silver: Cleansed Delta tables where timestamps are parsed, duplicates removed, and technician PII masked via SHA-256 hashing.
  • Gold: Business-ready Kimball dimensional star schema optimized with Delta V-Order for Direct Lake reporting.

Engineering Tradeoff: Storage footprint increases due to multi-layer persistence. This is mitigated by implementing automated OneLake cold tiering (30-day lifecycle retention).

Why Power BI Direct Lake mode instead of Import or DirectQuery?

The Architectural Driver: Traditional Power BI Import mode requires scheduled model refreshes (causing data latency and hitting memory size limits), while DirectQuery translates DAX queries into T-SQL on the fly (introducing severe query latency and database compute overhead).

Why Direct Lake was Chosen: Direct Lake mode allows Power BI's Analysis Services VertiPaq memory engine to read Delta Parquet files directly from OneLake storage without data duplication or scheduled imports. When Spark or Fabric pipelines update Gold Delta tables, Power BI instantly reflects the latest records with in-memory VertiPaq query speeds (< 250ms).

Engineering Tradeoff: Direct Lake requires Gold Delta tables to adhere to strict schema constraints (standard Delta Parquet with V-Order compression). Queries that exceed capacity memory limits fallback to DirectQuery mode.

What happens to malformed telemetry? (5-Worker DLQ Remediation)

The Architectural Driver: In physical IoT systems, hardware glitches produce malformed JSON, dropped timestamps, or out-of-range sensor readings. Simply dropping bad records hides upstream hardware degradation, while letting them enter Silver tables corrupts analytical aggregates.

How the DLQ Flow Operates: Fabric Eventstream applies schema validation filters and routes failed packets to a dedicated Dest_DeadLetterTelemetry quarantine table. The automated Notebook_DeadLetter_Remediation executes a 5-worker self-healing pipeline:

  • Worker 01: Validates payload schemas and isolates unparseable records.
  • Worker 02: Repairs null primary keys using deterministic facility-zone lookup tables.
  • Worker 03: Filters electrical noise and clips sensor anomalies into valid bounds.
  • Worker 04: Standardizes physical units (e.g., Fahrenheit to Celsius).
  • Worker 05: Enriches valid records and appends diagnostic traces to fact_dead_letter_governance.

Engineering Outcome: Achieved a 66.1% automated remediation rate on simulated anomalies while preserving 100% data auditability.

How is Security and Governance handled (RLS & DDM)?

The Architectural Driver: Multi-region agricultural operations require regional facility managers to only access telemetry and work orders within their geographic jurisdiction, while protecting technician personal contact information.

How Security is Enforced: Row-Level Security (RLS) is enforced at the warehouse database engine via an inline table-valued security predicate function (Security.fn_SecurityPredicate_FacilityRegion) bound to fact tables through a Security Policy. Sensitive technician telephone and email details are dynamically masked using SQL Dynamic Data Masking (DDM).

Distinction from Production IAM: In this portfolio implementation, security behavior is validated using simulated execution contexts. In an enterprise production deployment, these predicates would be bound directly to Microsoft Entra ID role claims and security groups.

Positioning & Maturity Statement

Portfolio Implementation vs. Production Deployment

This project demonstrates how I approached the architecture, implementation, testing, and operational concerns of an end-to-end data platform in a public environment. It is not a claim of operating the same platform in a production organization with real paying users, formal SLAs, enterprise identity federation, production capacity sizing, and multi-team operational ownership.

What I Would Change for a Real Enterprise Production Deployment

To demonstrate clear engineering judgment, the cards below contrast how capabilities are implemented in this public portfolio demonstration versus how they would be architected in an enterprise organization:

01

Secrets & Credential Management

Portfolio Implementation

Environment-based configuration (.env files) is sufficient for local simulator execution, unit tests, and the public architectural demonstration.

Enterprise Production

Secrets, connection strings, and tokens must be stored in Azure Key Vault with automated rotation and accessed strictly via Microsoft Fabric Managed Identities without persisted credentials.

02

Enterprise Identity (IAM) & Governance

Portfolio Implementation

Security behavior is validated through the implemented SQL Row-Level Security predicate functions and simulated role/context test suites (e.g., Operator_Benguet).

Enterprise Production

Authorization flows would integrate natively with Microsoft Entra ID security groups, automated SCIM provisioning, and Microsoft Purview data catalog classification tags.

03

CI/CD & Release Automation

Portfolio Implementation

Platform artifacts (TMDL semantic models, KQL scripts, DDL) were authored, tested, and validated within the available Fabric workspace environment with GitHub Actions unit testing.

Enterprise Production

Requires multi-stage Fabric Git Integration with strict branch promotion (Dev → Test → Prod), automated validation pipelines, PR approvals, and deployment rollback telemetry.

04

Capacity Sizing & Workload Isolation

Portfolio Implementation

The solution was developed and benchmarked on an evaluation Microsoft Fabric Trial (FT64) capacity with single-tenant streaming workloads.

Enterprise Production

Capacity sizing (e.g., Reserved F64/F128), multi-workload isolation (separating Spark ETL from Direct Lake memory), burst smoothing, and cost controls would be tuned to actual user traffic.

Honest Engineering Boundaries

Project Limitations & Measurement Boundaries

A critical mark of engineering maturity is knowing the exact boundary of what was measured versus what requires enterprise production infrastructure:

•
Synthetic Telemetry Nuances: The Python simulator models realistic diurnal cycles, pump degradation curves, and anomalies, but synthetic telemetry cannot reproduce every edge-case electrical failure or physical hardware degradation mode of physical sensors.
•
Workload & Concurrency Bounds: Portfolio ingestion benchmarks demonstrate platform throughput under controlled simulated batch runs, but do not represent 24/7 continuous enterprise multi-tenant query concurrency.
•
Trial Compute vs. Dedicated Enterprise Capacity: Fabric Trial capacity (FT64) provides shared compute evaluation, which differs from dedicated enterprise capacity with hard governance, background job throttling, and cross-workspace billing.
•
Simulated Identity vs. Enterprise IAM: Simulated session context proves that Row-Level Security predicates work mathematically, but does not substitute for corporate Entra ID directory synchronizations and OAuth token exchanges.
•
Modeled Storage vs. Actual Invoice Savings: The modeled 62% storage reduction represents file size tiering calculations between NVMe hot cache and Delta Parquet, rather than a realized corporate billing invoice.
•
Ingestion Latency vs. End-to-End Alert Delivery: The measured p50 latency (1.70s) and max latency (5.38s) represent Eventstream-to-KQL ingestion speed, which is distinct from multi-channel alert delivery latency (Teams/Email webhooks) under public internet congestion.
