Chapter 01

Why I Built This

Inspecting hydroponic leafy green tiers and ambient monitoring points in a vertical farm.

I spent time around a real vertical farming environment and saw firsthand how many physical variables shift throughout the day: greenhouse microclimates, irrigation line pressure, dosing pumps, lighting photoperiods, and biological crop conditions.

Being around that physical operation made me interested in what an end-to-end data platform behind it should look like—from high-frequency sensor ingestion to historical dimensional modeling.

I also had experience working around a local company in this agricultural space. Because the company's identity, internal systems, and production operational data are protected by a Non-Disclosure Agreement (NDA), I cannot publicly publish the actual implementation or proprietary telemetry.

Instead of setting the work aside, I recreated the entire engineering problem publicly. I built a standalone Python application that generates realistic synthetic telemetry, and then engineered a full Microsoft Fabric platform around that simulator to demonstrate the architectural patterns without disclosing confidential information.

Why the Data Is Simulated

HydroGrow Solutions is a fictionalized case-study identity created specifically for this public demonstration. The public repository contains 100% synthetic telemetry generated by Python, ensuring complete transparency while preserving real-world architectural integrity.

# Verbatim code excerpt from the simulator engine
class EnvironmentalTelemetryGenerator(BaseTelemetryGenerator):
    """Generates continuous microclimate readings for vertical growing zones."""

    def generate_event(self) -> EnvironmentalTelemetryEvent:
        facility = self.random_manager.choice(self.settings.facilities)
        zone = self.random_manager.choice(facility.zones)
        
        # Calculate diurnal solar cycle & HVAC thermal response
        ambient_temp = self.environment_manager.get_zone_temperature(facility.id, zone.id)
        relative_humidity = self.environment_manager.get_zone_humidity(facility.id, zone.id)
        co2_ppm = self.environment_manager.get_zone_co2(facility.id, zone.id)
        
        # Intentional anomaly injection for testing Fabric Activator alerts
        if self.settings.enable_ingestion_anomalies and self.random_manager.random() < 0.02:
            ambient_temp += self.random_manager.uniform(8.5, 14.0)  # Thermal runaway spike

        return EnvironmentalTelemetryEvent(
            event_type=EVENT_TYPE_ENVIRONMENTAL,
            facility_id=facility.id,
            zone_id=zone.id,
            sensor_type="ambient_temperature",
            sensor_value=round(ambient_temp, 2),
            unit="celsius",
            sensor_status=SENSOR_STATUS_HEALTHY if ambient_temp < 32.0 else SENSOR_STATUS_WARNING,
            is_daytime=self.environment_manager.is_daytime(),
        )

Layer 01 — Streaming & Operational Path

Real-Time Ingestion & Eventhouse KQL Database

Events from the Python simulator are received by Microsoft Fabric Eventstream via a dedicated Custom App endpoint. The stream partitions and routes events to 9 specific targets. Real-time telemetry is ingested directly into SmartFarmingKQLDB inside an Eventhouse, where continuous update policies and materialized views pre-aggregate microclimate metrics.

9 Eventstream destinations including Dead-Letter sink

Operational Dashboard

Layer 02 — Historical Analytics Path

OneLake Medallion Architecture (Bronze ➔ Silver ➔ Gold)

Historical telemetry is curated within SmartFarming_Lakehouse using Microsoft Fabric custom schemas. Data quality progressively increases as records move from raw append files to cleansed tables and finally into a production Kimball Star Schema.

Bronze Schema
Immutable append-only Delta tables via 9 Zero-Copy shortcuts
Silver Schema
Cleansed, deduplicated, and SHA-256 PII-masked tables
Gold Schema
Kimball Star Schema optimized with Delta V-Order
Layer 03 — Data Warehousing

Kimball Dimensional Model (6 Dimensions, 8 Fact Tables)

Rather than building isolated KPI aggregates, the Gold layer models the farming domain into conformed dimensions (facilities, zones, crops, equipment, technicians, dates) and granular business facts (environmental daily, equipment telemetry, crop yield, maintenance SLA, and dead-letter governance).

Conformed Dimensions
dim_facility, dim_zone, dim_crop, dim_equipment, dim_technician, dim_date
Business Fact Tables
8 fact tables covering operations, biological yield, SLA, and governance
Storage Optimization
Z-Order clustering on (facility_id, timestamp) for partition pruning
Layer 04 — Business Intelligence

Power BI Direct Lake Semantic Modeling

The enterprise semantic model (defined in TMDL format) connects directly to Gold OneLake Delta Parquet files using Direct Lake mode. This queries cold storage data directly with in-memory performance, completely bypassing scheduled import refreshes and dataset size limits.

Layer 05 — Incident Response & DataOps

Real-Time Alerting (Fabric Activator) & 5-Worker DLQ Remediation

Fabric Activator (Reflex) monitors live streaming events and triggers automated actions for operational farm anomalies (pH drift, thermal spikes) and DataOps engineering issues (ingestion latency, DLQ spikes). Corrupted payloads are quarantined into a dedicated Dead-Letter table and remediated via an automated 5-worker notebook process.

Layer 06 — Security & Governance

Regional Row-Level Security (RLS) & Dynamic Data Masking (DDM)

Security is enforced at the warehouse engine level using an inline table-valued predicate function (fn_SecurityPredicate_FacilityRegion) and Security Policies, ensuring regional facility operators can only view data from their assigned geographic jurisdiction. Sensitive operator contact info is dynamically masked using SQL DDM.

Chapter 07

Engineering Decisions & Notes

Detailed technical rationale behind architectural choices, honest project limitations, and production deployment considerations.

Why Eventhouse and KQL for the real-time path instead of SQL?

In high-frequency IoT streaming, relational databases struggle with write locks during high-concurrency append operations. KQL (Kusto Query Language) in Eventhouse is optimized specifically for append-only time-series data with automatic indexing, native time-window aggregation, and continuous update policies. This allows sub-second analytical queries on millions of records without impacting write performance.

Why build a Kimball Star Schema in the Gold layer rather than querying raw Silver tables?

Querying raw or semi-cleansed Silver tables directly creates high query complexity for reporting tools and risks inconsistent business calculations. A Kimball dimensional model provides conformed, reusable dimensions (facilities, zones, crops, dates) connected to business fact tables. This separation simplifies Power BI DAX calculations and optimizes Delta Parquet files for sub-second Direct Lake cache queries.

How does Power BI Direct Lake mode query OneLake Delta Parquet without import refreshes?

Traditional Power BI modes require either scheduled imports (copying data into memory) or DirectQuery (translating DAX into slow SQL queries). Direct Lake loads Delta Parquet files directly from OneLake into the Power BI Analysis Services VertiPaq memory engine using V-Order column compression. When Gold tables are updated by Spark, Power BI automatically sees the latest data without executing a scheduled model refresh.

How does the Dead-Letter Queue (DLQ) and remediation process protect Gold tables?

When malformed JSON, null identifiers, or out-of-bounds sensor readings arrive at the Eventstream, routing rules isolate those packets into a dedicated Dest_DeadLetterTelemetry destination. The Notebook_DeadLetter_Remediation job processes these quarantined records, applies schema repair rules, and logs diagnostic traces to fact_dead_letter_governance without blocking the primary ingestion stream.

How are Regional Row-Level Security (RLS) and PII masking enforced?

Row-Level Security is enforced at the warehouse database engine using an inline table-valued function (Security.fn_SecurityPredicate_FacilityRegion) bound via a Security Policy. When a query runs, the user's execution context is checked against assigned geographic regions. Sensitive operator contact information is masked using SQL Dynamic Data Masking (DDM) to comply with data privacy policies.

What I Would Change for a Real Production Deployment

While this public implementation demonstrates production-style architecture and engineering patterns using synthetic data on Microsoft Fabric Trial, a formal enterprise deployment would incorporate the following additional controls:

01. Secrets Management

Replace local environment files with Azure Key Vault and Fabric Managed Identities for automated credential rotation.

02. Enterprise Identity (IAM)

Bind Row-Level Security directly to Microsoft Entra ID security groups rather than manual session context simulation.

03. Automated Release CI/CD

Connect Microsoft Fabric Git Integration to an automated pull-request promotion pipeline with integrated integration test gating.

04. Capacity Autoscale

Transition from evaluation capacity (FT64) to production Reserved Instances (F64/F128) with automated bursting alerts.
